# ScamShield Nepal API

FastAPI API for authentication, owner-scoped scan history, explainable local analysis, and administrator tools. It does not query external URL reputation services or open submitted URLs. Screenshot OCR is optional at runtime and uses the local Tesseract executable; images are not stored.

## Local setup (Windows PowerShell)

```powershell
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
```

Edit `backend/.env` and replace `SECRET_KEY` with a value generated by:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

The checked-in example contains placeholders only. `.env` is ignored by Git. Install Tesseract OCR separately for local screenshot OCR; the production Docker image installs the English OCR package. Set `OCR_LANGUAGES=eng+nep` and install Nepali Tesseract data if Nepali OCR is needed.

Initialize or upgrade the schema, then run the API:

```powershell
alembic upgrade head
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

In another terminal, run the existing React app from the repository root:

```powershell
npm run dev
```

Copy root `.env.example` to `.env.local` if needed. Set `VITE_API_BASE_URL=http://localhost:8000`. The browser API URL must be the backend origin, with no `/api/v1` suffix. Both root-level paths and `/api/v1` aliases are available. Production analysis requires `VITE_API_BASE_URL`; the local heuristic demo can be explicitly enabled with `VITE_DEMO_MODE=true`.

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `SECRET_KEY` | Yes | JWT signing secret, at least 32 characters; use a generated value |
| `DATABASE_URL` | Production | PostgreSQL URL in production; local default is SQLite in `backend/scamshield.db` |
| `ENVIRONMENT` | Production | Set `production` to enforce PostgreSQL, HTTPS CORS origins, secure cookies, and no reset-token disclosure |
| `FRONTEND_ORIGIN` | Production | Exact HTTPS frontend origin |
| `CORS_ORIGINS` | Production | Comma-separated exact origins; wildcard origins are rejected |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | No | Normal session lifetime; defaults to 1,440 minutes |
| `RESET_TOKEN_EXPIRE_MINUTES` | No | Reset-token lifetime, 1–60 minutes; defaults to 15 |
| `SCAN_RETENTION_DAYS` | No | Stored scan metadata lifetime; defaults to 90 days |
| `OCR_LANGUAGES` | No | Tesseract language codes; defaults to `eng` |

The React client uses a bearer token only in memory/sessionStorage for compatibility and the API also sets an HttpOnly session cookie. Auth tokens are removed from legacy localStorage on startup. For persistent cross-origin cookies, use frontend and API hostnames under the same site where possible; browser third-party-cookie restrictions can affect unrelated Vercel/Render domains.

## Database and data handling

Use PostgreSQL for production. Migrations are managed by Alembic:

```powershell
alembic upgrade head
alembic current
```

Scan content is not retained by default: message bodies and screenshot images are not stored; message evidence is redacted, screenshots are OCR-processed in memory, and URL history stores the hostname without query/path. Authenticated history is stored per owner. Users can delete one scan or clear their full history. The default metadata retention period is 90 days; schedule this command daily in the host's scheduler:

```powershell
python -m app.retention
```

The command deletes only expired scan rows. It does not delete accounts or audit records.

## First administrator

After migrations, create the first administrator from a trusted machine. The command prompts for a 12-character minimum password; it never accepts a password in command-line arguments:

```powershell
python -m app.seed bootstrap-admin --email admin@example.com
```

If an existing development database has an administrator created by the old demo seed, rotate that account's password and revoke its existing sessions:

```powershell
python -m app.seed rotate-admin --email admin@scamshield.np
```

Public registration always creates regular users. No public admin-registration route exists. Do not deploy old demo SQLite files; they contain demo accounts and are excluded from future Git commits. Existing Git history may still contain those files, so rotate any known demo passwords and rewrite repository history before making that history public.

## Tests

Tests run against a separate in-memory SQLite database and do not call a running server or mutate local databases:

```powershell
pytest -q
```

The old `backend/test_api.py` live-server script has been replaced with isolated pytest coverage.

## Deployment

The repository includes `backend/Dockerfile` and root `render.yaml` for a separate Docker web service plus managed PostgreSQL. This is preferable for the current OCR workload and persistent database. Render pre-deploy migrations require a plan that supports pre-deploy commands. Select a suitable service/database plan in Render before deploying; deployment has not been run from this project.

1. Create the Render services from `render.yaml` and configure/confirm the service and PostgreSQL plan.
2. Set `FRONTEND_ORIGIN` and `CORS_ORIGINS` to the exact Vercel origin you use. If it changes, update both values.
3. Keep Render's generated `SECRET_KEY`; do not copy it into Vercel or source files.
4. The pre-deploy command runs `alembic upgrade head`. `/health` checks database connectivity.
5. Configure Vercel `VITE_API_BASE_URL` to the Render API origin and `VITE_DEMO_MODE=false`, then redeploy the frontend.
6. Bootstrap or rotate the first admin through a one-off shell on the deployed service after migrations.
7. Configure a daily scheduled run of `python -m app.retention` if automatic 90-day deletion is required.

Vercel's current Python Functions runtime can host FastAPI, but its function request/response payload limit is 4.5 MB. A 5 MB screenshot expands beyond that limit when encoded as JSON, and the app needs a persistent PostgreSQL connection and a native Tesseract executable. A separate Docker service avoids these constraints for this implementation. See [Vercel Python runtime docs](https://vercel.com/docs/functions/runtimes/python), [Vercel function limits](https://vercel.com/docs/functions/limitations), and [Render FastAPI deployment docs](https://render.com/docs/deploy-fastapi).

## Implemented capabilities and limitations

- Registration, Argon2id password hashing (legacy bcrypt verification/upgrade), bearer compatibility, HttpOnly session cookies, CSRF checks for cookie-authenticated writes, session revocation, reset-token hashing, and database-backed authentication rate limits.
- Text warning-sign rules, strict URL parsing and hostname checks without outbound requests, PNG/JPEG validation, optional local OCR, owner-scoped history/profile/statistics, admin authorization, last-active-admin protection, audit logs, pagination, and 90-day cleanup command.
- Password-reset email delivery is not configured. Development mode exposes a reset token for local testing; production intentionally does not expose it. Production users need administrator-assisted recovery until an email provider is configured.
- URL reputation, redirect destination, live page content, identity, payment settlement, and sophisticated image manipulation are not verified. A clean result is not proof of safety or funds received.
- OCR quality depends on Tesseract and installed language data. The local demo engine is not the production detector.
- Render/Vercel deployment, database provisioning, SMTP, and scheduled retention have not been executed; account credentials and service selection are required.
